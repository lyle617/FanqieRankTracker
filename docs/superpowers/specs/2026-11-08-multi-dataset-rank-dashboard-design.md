# 男频女频双榜单与短篇推荐设计

## 意图

在当前男频版本的提交 `c235c5f` 基础上，吸收上游的 Actions 稳定性修复和短篇推荐页面，同时让同一套看板支持男频、女频两套独立榜单数据。现有男频链接和 API 继续可用，新增女频入口和短篇入口。

## 目标

- 每日工作流同时抓取男频和女频新书榜，并分别生成趋势、AI 摘要和静态 API。
- 首页通过数据集切换器选择男频或女频，日期、分类、趋势和书籍详情都跟随当前数据集。
- 保留现有男频拆文库抓取；女频先支持榜单和趋势，不复制男频专属拆文逻辑。
- 接入上游短篇推荐页面、导航样式和安全的外部数据加载。
- 保留 `data/latest_ranks.json`、`api/lastest/*` 等男频旧路径，避免现有链接失效。

## 非目标

- 不把男频和女频历史快照混到同一个 `dates.json` 或趋势目录。
- 不把上游女频生成的全部历史归档直接覆盖当前男频数据。
- 不把短篇外部 API 改造成仓库内的爬虫或服务端代理。

## 约束

- 上游当前版本默认是女频，不能直接覆盖当前男频入口、文件前缀、分类分组或 AI 提示词。
- GitHub Actions 需要使用上游已验证的新版本 Action、非取消式写入并发组，以及榜单入口重试。
- 工作流中的两个数据集必须顺序写入同一个分支，避免两个自动提交互相覆盖。
- 本地 `venv/`、`__pycache__/` 等环境目录不进入仓库。

## 方案与选择

考虑过三个入口方案：为男频和女频分别维护页面；保留男频首页并新增女频页；以及在同一首页切换数据集。选择第三种，因为两套榜单的卡片、趋势和日期交互相同，统一入口可以避免复制维护；数据和构建产物仍按数据集分开，因此不会把两类历史混合。

## 结构

- 当前 `data/` 根目录继续作为男频兼容目录。
- 现有 `data/female_archive/` 重命名为 `data/female/`，作为女频快照、日期、趋势和最新聚合数据目录。
- 新增数据集配置，描述标签、快照前缀、最新数据、日期索引、趋势目录、市场摘要和 API 根路径。
- `scrape_fanqie_ranks.py` 增加 `--dataset male|female`，共享抓取流程，仅切换榜单 URL、分类前缀、输出目录和文件前缀。
- `scripts/build_latest.py` 增加数据集参数，保留男频与女频各自的分类分组、关键词和提示词。
- `js/app.js`、`js/trend.js`、`js/book.js` 根据 URL 数据集参数读取对应配置；导航链接保留当前数据集。
- 从上游接入 `shorts.html`、`js/shorts.js` 及相关样式，短篇页面使用上游外部 API，并从榜单页面提供入口。
- `.github/workflows/scrape.yml` 和 `force_update.yml` 顺序处理两个数据集；男频继续执行章节抓取。

## 合并策略

先将上游合并提交落到当前基线，保留上游短篇页面、Actions 升级、并发控制、重试和测试；对女频默认实现与当前男频实现的冲突，按上述双数据集结构解决。数据文件按目录归属保留，最后补齐双数据集构建和前端切换测试。

## 验收标准

- 本地构建能分别为男频和女频生成 `latest_ranks.json`、日期索引、趋势和 API。
- 首页切换数据集后，最新榜单、历史日期、趋势页和书籍详情不会读取另一套数据。
- 短篇页面可打开、切换标签、处理空结果和外部 API 错误。
- Python 测试和语法检查通过；工作流 YAML 可解析；提交后 GitHub Actions 可手动运行验证。
